# OpenEvidence Selection Opener

OpenEvidence Selection Opener is a lightweight Chrome extension for clinicians,
students, and evidence-based medicine readers. Select text on a whitelisted page,
click `Ask OpenEvidence`, and the extension opens the selection in OpenEvidence
right next to the current tab. With a validated Groq API key, it can also rewrite
selected recall-style text into editable foreground questions before sending them
to OpenEvidence.

![Selection toolbar demo](docs/demo-toolbar.png)

## Features

- Selection toolbar anchored above highlighted text.
- `UpToDate` and `Google` buttons to search the selection beside the current tab.
- Right-click `Ask OpenEvidence` context menu for pages and Chrome PDF selection fallback.
- Opens OpenEvidence beside the current tab, optionally in the background.
- Local query history with a dedicated options tab, recording each text sent to OpenEvidence (plus the original selection, prompt, and transformed text for `PICO`/custom rewrites).
- Whitelist-based activation, including `file:///*` support.
- BYOK Groq integration stored in `chrome.storage.local`.
- Built-in `PICO` rewrite flow for evidence-based medicine questions.
- Custom prompt buttons with user-defined names and prompt instructions.
- Editable LLM output panel with `Copy`, `Ask OpenEvidence`, and `Close`.
- NCCN guideline PDF links on OpenEvidence redirected to your own viewer, in a tab and in the side pane alike.
- Hospital formulary (院內品項) lookup: import your drug list, then check whether a selected drug is stocked and which in-house items share its ingredient or mechanism (ATC).
- Light, dark, or system appearance modes.
- No runtime framework, no remote UI dependencies.

## Default Whitelist

```text
https://ankiuser.net/study
https://www.openevidence.com/*
http://uptodate.com/*
nejm.org/*
file:///*
```

Entries are URL prefixes. `*` can be used as a wildcard.

## Install From Release

1. Download the latest `oe-extension-vX.Y.Z.zip` from [Releases](https://github.com/htlin222/oe-extension/releases).
2. Unzip it.
3. Open `chrome://extensions`.
4. Enable Developer mode.
5. Click `Load unpacked`.
6. Select the unzipped extension folder.

The release also includes a `.crx` artifact generated by GitHub Actions.

## Install From Source

```bash
git clone https://github.com/htlin222/oe-extension.git
cd oe-extension
npm test
npm run build
```

Then load `dist/extension` from `chrome://extensions`.

## Local PDF Support

For local PDF files opened in Chrome:

1. Open `chrome://extensions`.
2. Open this extension's details.
3. Enable `Allow access to file URLs`.

Chrome's built-in PDF viewer may not expose selection events to content scripts.
When the floating toolbar does not appear, use the right-click context menu:
select text, right click, choose `Ask OpenEvidence`.

## NCCN Link Redirect

OpenEvidence cites NCCN guidelines as links to `nccn.org` PDFs, which are behind
a login. This extension rewrites those links to a viewer you control, keeping the
guideline slug and page number.

It runs in a full OpenEvidence tab and inside the side pane. Because the side
pane hosts OpenEvidence in an iframe, a redirected link there always opens in a
new tab, so the side pane stays on the conversation.

Configure it under `Settings` in the options page:

- `Redirect NCCN guideline links` turns the rewrite on or off (on by default).
- `Redirect URL template` accepts two variables:
  - `$cancer` &mdash; the guideline slug, such as `b-cell`;
  - `$page` &mdash; the page number, defaulting to `1`.

| Target              | Template                                                           |
| ------------------- | ------------------------------------------------------------------ |
| Web viewer          | `https://nccn.hsiehting.com/preview/$cancer?page=$page`            |
| Local (macOS/Linux) | `file:///Users/YOUR_NAME/Downloads/NCCN/$cancer.pdf#page=$page`    |
| Local (Windows)     | `file:///C:/Users/YOUR_NAME/Documents/NCCN/$cancer.pdf#page=$page` |

`file://` templates need `Allow access to file URLs` enabled, as described under
[Local PDF Support](#local-pdf-support).

## Hospital Formulary (院內品項)

Import your hospital's drug list under the `院內品項` tab in the options page
(`.xlsx` or `.csv`; XLSX reads the first sheet, CSV may be UTF-8 or Big5). The
header row needs a `藥名` column; `批價碼`, `ATC碼`, `藥理代碼`, `劑型`, `健保價`,
`自費價`, and storage columns such as `P1儲位` / `藥庫` are used when present.

After import, the selection toolbar shows a `院內` button. It lists:

- **院內有此藥** &mdash; items matched by generic name, brand name (English or
  Chinese), or billing code;
- **同成分其他品項** &mdash; other items with the same 7-character ATC code;
- **同機轉** &mdash; items sharing the 5-character ATC chemical subgroup
  (e.g. `C10AA` statins, `A10BK` SGLT2 inhibitors).

Click a billing code to copy it.

When nothing in the list matches by name, the ATC code is looked up in order:

1. **NLM RxClass** (`rxnav.nlm.nih.gov`, free, no key). Candidate English drug
   names from the selection are resolved to RxNorm ingredients and their ATC
   level-4 class. A US brand such as `Lipitor` then lands on the in-house
   atorvastatin as same ingredient; an unstocked drug such as `ertugliflozin`
   lists in-house SGLT2 inhibitors (`A10BK`). Can be turned off on the
   `院內品項` tab. Chinese names are not in RxNorm.
2. **Groq** (only with a validated key), labelled as an AI guess to verify.

The list stays in `chrome.storage.local` on this computer; it is never synced
or uploaded. Only English words from the selection go to RxClass, and only the
selected text goes to Groq, each only when the in-house list has no match.

## Mobile Web App (院內查藥)

`web/` is a phone-friendly web app (PWA) with the same formulary lookup. It is
built with `npm run build:web` and deployed to GitHub Pages by
`.github/workflows/pages.yml` on every push to `main`.

**One shared list.** Convert the drug list to a Google Sheet, then use
`File → Share → Publish to web → CSV` and paste that link into the app's
settings (and into the extension's `院內品項` tab). Every phone and computer
downloads the list from that sheet and keeps an offline copy; editing the sheet
updates everyone. Anyone with the link can read the list, so share it only
with colleagues. `設定 → 複製設定連結` produces a link that configures a new
phone in one tap; the sheet URL travels in the `#fragment`, never reaching the
web server.

**Using it**

- Add to home screen: Safari → Share → *Add to Home Screen* (iPhone), or
  Chrome → menu → *Add to Home screen* / *Install app* (Android).
- Type or paste a drug name; results show in-house items, same ingredient
  and same mechanism, with copyable billing codes. Buttons send the same text
  to OpenEvidence, UpToDate, PubMed and Google.
- From OpenEvidence, a PDF or any app: select text → Share → 院內查藥
  (Android share target), or an iPhone Shortcut that opens
  `<app>#src=<sheet>&q=<text>`; the settings screen shows the exact URL.
- When nothing matches by name, NLM RxClass is queried as in the extension
  (Groq is not used in the web app).

## Phone App on Apps Script (院內查藥 · OE)

`gas/` is the extension rebuilt for phones as a Google Apps Script web app,
bound to the formulary Google Sheet so the list never has to be published.
It has the in-house lookup (院內有此藥 / 同成分 / 同機轉, RxClass fallback),
OpenEvidence / UpToDate / PubMed / Google buttons, `PICO` and custom prompts
(Groq key kept in script properties, custom prompts read from a `自訂提示` tab),
and an on-device history of what was sent to OpenEvidence.

For an in-app result, first distinguish the **page** and **text API** paths:

- `/exec?q=<URL-encoded text>` serves the full lookup page. The candidate iPhone
  share-sheet flow is **URL Encode → URL → Show Web View**, passing the complete
  URL to the last action. **Open URLs** launches the default browser (for example,
  Chrome), so it does not meet the requirement to keep the result over the source
  app. In the user's current Chinese UI the Web View action appears as
  `顯示網頁顯示方式`; its configured action reads `顯示 URL 的網頁顯示方式`.
- `GET /exec?api=lookup&q=...`, or `POST /exec` with a Form Text field named `q`,
  serves a plain-text lookup response **only after Google permits the request**.
  POST defaults to lookup and shares GET's token checks and 4,000-character limit.
  A Form request does not need manual URL encoding. The two-action
  **Get Contents of URL → Show Result** setup is conditional on this API being
  reachable in that client's authentication context; unit tests do not establish
  that a deployed GAS app works from iPhone Shortcuts.

Authenticated browsers, Shortcuts HTTP requests, and embedded web views must not
be assumed to share Google login state. An HTTP 200 can be a Google login HTML
page rather than a successful lookup. ContentService responses also redirect to
a one-time `script.googleusercontent.com` URL: follow redirects and inspect the
final content type/body; never save that temporary URL in a shortcut.

**Do not widen deployment or spreadsheet access to troubleshoot this flow.**
Preserve the current access policy and first test the existing authorized page in
Web View. Google may restrict embedded login, and a share-sheet Web View may have
platform-specific behavior; confirm a real result and return to the original app
on the target iPhone before calling the solution verified. Existing
`ACCESS_TOKEN` checks still apply when configured.

On 2026-11-09 the user confirmed all three acceptance checks on their iPhone:
the shared drug name populated the lookup and produced formulary results in the
embedded view, Chrome did not launch, and closing returned to the original
reading position. This verifies the existing authorized Web View flow on that
device, not unauthenticated API access or fresh Google login on other devices.
No data-access policy was changed to obtain this result.

See the [illustrated troubleshooting guide](docs/iphone-shortcut-guide.html) and
[HTTP findings and iPhone acceptance checks](docs/iphone-shortcut-diagnosis.md).

`gas/Code.gs` and `gas/Index.html` are the two files pasted into Apps Script;
both are generated by `npm run build:gas` from `src/formulary.js`, `web/style.css`
and the sources in `gas/`.

To update the Apps Script deployment:

1. Run `npm run build:gas`, or use the generated files committed on the same branch.
2. Replace the complete contents of `Code.gs` and the HTML file named `Index`
   with `gas/Code.gs` and `gas/Index.html` from that same build.
3. Save, then choose **Deploy → Manage deployments → Edit → New version → Deploy**.
   Updating GitHub or saving the script alone does not update an existing `/exec` deployment.
4. Reopen the deployment URL and check the build shown at the bottom of the page.

The page uses an Apps Script HTML template to inject startup data. A missing
startup object indicates an injection/deployment problem; it does not by itself
prove that `Code.gs` is old. Keep the `<?!= bootJson ?>` template expression in
`Index`; `doGet` evaluates it and escapes the JSON before inserting it.

## Groq BYOK

The `PICO` and custom prompt buttons appear only after a Groq API key is validated.

1. Open extension options.
2. Under `PICO rewrite`, click `Edit`.
3. Paste a Groq API key.
4. Click `Save`.

The key is stored locally with `chrome.storage.local`; it is not committed,
bundled, or sent anywhere except Groq API requests initiated by the extension.

## Custom Prompts

Custom prompts let you create extra buttons beside `Ask OpenEvidence` and `PICO`.
Each custom prompt has:

- a button name, such as `Dx`, `Summarize`, or `Guideline`;
- a prompt that tells Groq how to transform the selected text.

The model output is displayed in an editable panel. You can copy it or ask
OpenEvidence with the edited result.

## OpenEvidence URL

The extension opens selections with this URL shape:

```text
https://www.openevidence.com/ask?query=<selected text>&configName=prod&attachments=%5B%5D&_rsc=1pln2
```

## Release Workflow

Release packaging runs on GitHub release creation/publication:

- runs the test suite;
- builds `dist/oe-extension-v<version>.zip`;
- packs `dist/oe-extension-v<version>.crx`;
- uploads both files as release artifacts.

For stable CRX IDs across releases, add a repository secret named
`CRX_PRIVATE_KEY_BASE64` containing the base64-encoded Chrome extension private
key. Without that secret, CI still generates a `.crx`, but Chrome may assign a
new extension ID.
